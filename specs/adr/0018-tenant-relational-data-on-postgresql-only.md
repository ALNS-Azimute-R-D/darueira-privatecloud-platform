# ADR 0018: Tenant Relational Data on PostgreSQL Only — Decommission `tenant-mysql`

## Status
Accepted (2026-11-22). Amends ADR-0016, which listed `tenant-mysql` in the tenant PaaS baseline.

## Context
Every tenant environment received a `tenant-mysql` StatefulSet next to `tenant-postgres`. In practice the
platform has exactly one MySQL consumer: the `caseforce-legalhub-mgmt` backend (Micronaut / Kotlin) of tenant
`swfabrik-europe`. The `swfabrik-latam` instance has no consumer at all, and its data is empty.

Running two relational engines per tenant doubles the operational surface (upgrades, backups, probes, storage
volumes, NetworkPolicies, credentials, documentation) for no functional gain. The architectural recommendation of
the platform is PostgreSQL for relational and transactional data; `tenant-postgres` already hosts one database per
application (`drr_tnt_bizapps_db`, `drr_tnt_keycloak_db`, `DBBookAnythingPlatform`, `DBVoizeEHRIntegrator`).

## Decision

### 1. One relational engine per tenant: PostgreSQL
Tenant workloads that need a relational store use `tenant-postgres`. MySQL is no longer part of the tenant
baseline. `tenant-keycloak`, `tenant-minio`, `tenant-openbao` and `tenant-postgres` remain (`tenant-mongodb` was removed later by ADR-0019).

### 2. CaseForce moves to PostgreSQL
- A dedicated database `drr_tnt_caseforce_db`, owned by the least-privilege role `caseforce_app`
  (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE`), provisioned by `scripts/provision_caseforce_db.sh`
  (idempotent; the password is generated in memory and stored only in the Secret `caseforce-db`, never in Git).
- The backend runs its Flyway migrations as that role. The MySQL migrations V1..V8 (create, rename to the `tb_*`
  convention, drop, seeds, MySQL-only syntax) are replaced by a Postgres baseline in their final state:
  `V1__init_postgres.sql` (schema) and `V2__seed_data.sql` (seeds). The Flyway history is reset on purpose: the new
  database starts empty.
- MySQL idioms become their PostgreSQL equivalents: `AUTO_INCREMENT` -> `GENERATED BY DEFAULT AS IDENTITY`,
  `ON UPDATE CURRENT_TIMESTAMP` -> a `BEFORE UPDATE` trigger, `JSON` -> `JSONB`, `TIMESTAMP` -> `TIMESTAMPTZ`,
  `INSERT IGNORE` -> `ON CONFLICT DO NOTHING`, `JSON_CONTAINS` -> `jsonb_exists`. Foreign keys get explicit indexes
  (MySQL created them implicitly).
- Repositories use `Dialect.POSTGRES`; the integration tests use a PostgreSQL Testcontainer.

### 3. Decommission `tenant-mysql` in every tenant
For `swfabrik-europe` and `swfabrik-latam`: remove the StatefulSet, Service, PVC, PV, the `tenant-mysql-credentials`
Secret and the manifests under `platform/kustomize/base/tnt-tenant-base/` and `platform/kustomize/overlays/tenants/*`.
The deletion happens only after CaseForce runs on PostgreSQL. A dump of the MySQL `caseforce` database is taken first.
The host directory behind the PV is left in place (removing it needs root).

## Consequences
- **Positive:** one engine to operate, back up and secure; fewer volumes and policies; the credential for CaseForce is
  a dedicated role instead of a shared one.
- **Behavioural difference:** MySQL's default collation compared strings case-insensitively (`ds_email`, aliases,
  case numbers); PostgreSQL does not. CaseForce data is always written in lower case today, so nothing breaks, but new
  code must not rely on case-insensitive matching.
- **Data:** the MySQL `caseforce` database only held seed data (2 users, 4 roles, 1 partner agency); it is recreated by the
  Postgres seeds. Anything created by hand there is lost (the dump is the fallback).
- **Downtime:** the CaseForce backend uses the `Recreate` strategy, so it is unavailable for about a minute during the switch.
- **Rollback:** until the MySQL objects are deleted, rolling back is a chart revert (the old image and the MySQL variables
  are still in Git history). After the deletion, restoring needs the dump.
